## 1. 검토 목적

현재 구현이 최초 제품 목표보다 무거워졌기 때문에 제품 범위와 구현 우선순위를
다시 확정하려 한다.

이번 검토는 문장을 다듬는 작업보다 다음 판단에 집중한다.

1. 새 PRD가 최초 제품 목표를 올바르게 복원했는가?
2. 대시보드·거시지표를 유지하면서도 제품을 충분히 단순화했는가?
3. 고정 섹터를 요구하지 않는 구조가 일관적인가?
4. 현재 코드베이스를 재사용하는 편이 적절한가?
5. 제외 대상으로 분류한 기능이 실제로 불필요하거나 시기상조인가?

---

## 2. 사용자가 재확인한 제품 목표

> 기업 정보·기술 정보·정책 정보를 매일 모니터링하면서 중요한 지식을 체크하고
> 축적한다.

추가로 확정된 조건:

- 고정 섹터를 사전에 규정할 수 없으며 이를 반복해서 요구하면 안 된다.
- 경제 대시보드와 시장·거시지표는 반드시 필요하다.
- 기능을 무거운 인텔리전스 플랫폼으로 과도하게 설계하면 안 된다.
- 체크·메모·묶음이 실제 사용의 중심이다.
- 프로젝트를 계속할지 처음부터 다시 시작할지 판단할 수 있어야 한다.

## 5. 새 PRD의 핵심 구조

```text
기업 정보 ─┐
기술 정보 ─┼→ 매일 카드 수집 → 중요 체크 → 메모 → 묶음 → 검색·재활용
정책 정보 ─┘

시장·거시지표 → 경제 대시보드 → 위 자료를 해석하는 배경
```

핵심 화면:

- `/today`: 경제 현황 + 오늘 기업·기술·정책 카드
- `/archive`: 검색·필터
- `/cards/[id]`: 카드 상세·체크·메모·묶음
- `/collections`: 지식 묶음
- `/dashboard`: 경제지표 상세
- `/admin`: 사용자·수집 상태

## 7. Claude에게 요청하는 구체적 산출물

### A. P0/P1/P2 리뷰

- P0: 제품 정의 자체의 모순
- P1: MVP 범위를 다시 무겁게 만들 위험
- P2: 문구·데이터 모델·수용 기준 개선

### B. 기능 판정표

각 기능을 다음 중 하나로 분류:

- MVP 필수
- MVP 선택
- 후속
- 제거

### C. 데이터 모델 검토

다음 최소 모델이 충분한지 검토:

- `cards`
- `card_user_states`
- `notes`
- `collections`
- `collection_items`
- `indicators`
- `indicator_values`

특히 중요 체크와 메모가 사용자별인지 팀 공통인지에 따른 모델 차이를 제시해주길
요청한다.

### D. 재시작 판단

다음 두 대안을 비교:

1. 현재 저장소에서 과도한 기능을 비활성화하고 핵심 기능을 추가
2. 새 스키마·새 앱으로 처음부터 재구축

비교 기준:

- 데이터 마이그레이션 위험
- 삭제·정리 비용
- 인증·수집 기반 재사용 가치
- 테스트 신뢰도
- 장기 복잡도

최종적으로 한 가지를 권고하고 이유를 명시해주길 요청한다.

## 8. 반드시 지켜야 할 검토 전제

- 고정 섹터를 결정하라는 질문을 다시 제안하지 않는다.
- 대시보드와 시장·거시지표를 제거 대상으로 분류하지 않는다.
- 기업·기술·정책 3축 중 하나를 부차적 기능으로 축소하지 않는다.
- 사용자 2~3명 내부 도구라는 규모를 유지한다.
- AI·관계 그래프·복잡한 평가 모델을 기본값으로 제안하지 않는다.
- 새로운 기능을 제안할 때는 핵심 사용 흐름과 직접 연결되는 이유를 제시한다.

## 9. 현재 제안의 잠정 결론

현재 저장소를 완전히 폐기하지 않는다.

- 기술 기반은 재사용 가치가 있다.
- 제품 범위와 화면은 다시 설계해야 한다.
- 과도한 기능은 즉시 삭제하지 않고 비활성화한다.
- 중요 체크·메모·묶음·검색을 먼저 완성한다.
- 경제지표는 실제 공급자와 기준일을 명확히 해 유지한다.

이 결론은 Claude 리뷰와 사용자 승인 후 확정한다.
