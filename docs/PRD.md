# 스타트업 인텔리전스 아카이브 — 통합 PRD

버전 1.0 · 2026-07-24  
통합 기준: PRD v0.4 + Claude 수정본 + 개발 검토

---

## 1. 제품 정의

### 1.1 한 문장

특정 스타트업 섹터의 정책·뉴스·투자·기술 정보를 지속적으로 업데이트하고 누적해, 사용자가 **오늘 무엇이 중요하고 이전과 무엇이 달라졌는지 매일 확인할 수 있게 하는 인텔리전스 아카이브**다.

### 1.2 가치의 위계

제품 가치는 세 층으로 구분한다.

| 층 | 가치 | 제품에서의 의미 |
|---|---|---|
| 본질적 가치 | 업데이트와 누적 | 관련 정보를 놓치지 않고 계속 보존한다 |
| 일일 사용 가치 | 정보가치와 맥락 | 오늘 볼 정보와 이전 대비 변화를 빠르게 파악한다 |
| 축적 차별성 | 연결과 해석 | 과거 정보와 사용자 해석이 쌓여 장기 자산이 된다 |

사용자는 아무것도 작성하지 않아도 매일 제품에서 가치를 얻어야 한다. 메모·연결·판단은 정보의 수명과 재사용성을 높이는 선택적 레이어다.

로드맵 우선순위가 갈릴 때는 다음 순서를 따른다.

1. 업데이트의 안정성과 카드 품질
2. 오늘 화면과 과거 맥락
3. 선택적 해석과 브리핑

### 1.3 제품의 북극성 문장

> **오늘의 변화를 놓치지 않게 하고, 어제의 정보가 사라지지 않게 한다.**

## 2. 해결하려는 문제

스타트업 관련 정보는 여러 출처에 흩어져 계속 갱신된다.

- 정부 정책과 지원사업은 여러 기관에 분산돼 있다.
- 투자·제휴·기업 동향은 기사와 발표 자료로 흩어진다.
- 기술 변화는 논문·특허·산업 자료에 따로 나타난다.
- 개별 정보는 읽고 나면 사라지고 과거 사건과 비교하기 어렵다.
- 정보량이 늘수록 매일 무엇부터 봐야 하는지 판단하기 어렵다.
- 팀이 남긴 메모와 판단은 메신저·회의·개인 기억에 흩어진다.

이 제품은 다음 질문에 빠르게 답하게 한다.

1. 오늘 새로 들어온 중요한 정보는 무엇인가?
2. 어제 또는 지난주와 비교해 무엇이 달라졌는가?
3. 어떤 기업·정책·기술 흐름과 연결되는가?
4. 더 깊이 추적할 항목은 무엇인가?
5. 우리 팀은 중요한 정보에 어떤 해석을 남겼는가?

## 3. 목표와 비목표

### 3.1 목표

1. 한 섹터의 주요 정보를 매일 안정적으로 수집한다.
2. 중복과 저가치 정보를 줄여 읽을 만한 카드로 정리한다.
3. 오늘의 주요 변화와 신규 신호를 한 화면에서 보여준다.
4. 기업·정책·주제별로 과거 정보를 누적한다.
5. 새 정보에 관련 과거 사건을 연결한다.
6. 사용자가 필요할 때 메모·연결·판단을 남기게 한다.
7. 운영자와 사용자가 카드의 출처와 선정 이유를 확인하게 한다.

### 3.2 Phase 1 비목표

- 네 개 이상의 이질적인 소스를 동시에 완성
- 실시간 속보 경쟁
- 시장·거시 지표 상황판
- 복잡한 그래프와 자동 변곡점 탐지
- 벡터 검색과 별도 검색 엔진
- AI 판단·묶음 자동 생성
- 외부 공유·PDF·메일 발송
- 다중 섹터·다중 테넌트
- 완전 자동화된 기업 명부
- 정교한 개인화 추천

## 4. 사용자와 핵심 사용 장면

### 4.1 사용자

| 사용자 | 필요한 가치 |
|---|---|
| 관리자 | 소스·키워드·명부를 운영하고 카드 품질을 교정한다 |
| 큐레이터 | 매일 중요 정보를 확인하고 필요할 때 해석을 남긴다 |
| 열람자 | 정리된 정보와 브리핑을 읽는다 |

Phase 1은 관리자와 큐레이터만 지원한다.

### 4.2 아침 확인

사용자는 5~10분 안에 다음을 확인한다.

- 오늘의 주요 업데이트 5~10건
- 새 신호와 기존 사건의 후속 업데이트
- 새로 발견된 기업
- 계속 추적할 주제

### 4.3 주제 탐색

사용자는 기업·정책·기술 키워드를 기준으로 최신 정보와 과거 사건을 함께 본다.

### 4.4 선택적 해석

사용자는 중요한 카드에 메모를 남기거나 여러 카드를 연결한다. 해석을 남기지 않아도 정보 피드와 아카이브의 핵심 기능은 완전하게 작동한다.

## 5. 개념 모델

### 5.1 정보 층

| 객체 | 역할 | 생성 |
|---|---|---|
| 원천 `Source Item` | 수집한 원문과 메타데이터 | 시스템 |
| 카드 `Card` | 중복을 줄이고 읽기 쉽게 정리한 정보 단위 | 시스템 + 관리자 |
| 명부 `Company` | 섹터 기업과 별칭·근거 | 시스템 후보 + 관리자 승인 |
| 주제 `Topic` | 정책·기술·시장 탐색 축 | 시스템 + 관리자 |
| 일일 업데이트 `Daily Update` | 오늘 볼 가치가 높은 카드의 정렬 결과 | 규칙 + 관리자 |

### 5.2 해석 층

| 객체 | 역할 |
|---|---|
| 메모 | 카드 한 건에 대한 짧은 관찰 |
| 연결 | 여러 카드 또는 과거 사건의 관계 |
| 판단 | 정보가 의미하는 기회·위험·변화에 대한 해석 |
| 브리핑 | 선택한 카드와 해석의 편집 결과 |

메모·연결·판단은 하나의 `Annotation` 모델과 공통 작성 화면을 사용한다.

### 5.3 스타트업 명부

스타트업 여부를 직접 판정하지 않고 생태계의 확인 근거를 누적한다.

- 정부 지원사업 선정 명단
- TIPS 선정기업
- AC/VC 포트폴리오
- 데모데이 참가 명단
- 자기선언 플랫폼

확신도는 단순 근거 개수가 아니라 다음 요소를 사용한다.

- 근거 유형과 신뢰 가중치
- 서로 독립적인 원천인지
- 확인 시점
- 관리자 승인 상태

Phase 1에서는 수동 등록과 카드에서 발견한 후보 승인만 제공한다.

### 5.4 범위 판정

| 환 | 내용 | 수집 정책 |
|---|---|---|
| 0환 | 명부 기업에 매칭된 데이터 | 무조건 |
| 1환 | 자본·제도 | 무조건 |
| 2환 | 기술 기반 | 앵커 조건 일치 시 |
| 3환 | 산업·시장 | 통과 근거 한 줄 필수 |

환은 소스가 아니라 카드와 명부의 매칭 결과다.

### 5.5 깊이 분류

1. 공식 연구 산출물인가? → `research`
2. 시의성이 생명인가? → `news`
3. 나머지 분석·지식 자료인가? → `tech`

깊이와 환은 파이프라인·관리 화면에서 사용한다. 일반 화면에는 정책·지원 / 기업·투자 / 기술·시장 주제만 노출한다.

## 6. 핵심 화면

### 6.1 오늘 `/today`

기본 진입 화면이다.

#### 상단

- 오늘 새 카드 수
- 주요 업데이트 수
- 새 기업 후보 수
- 마지막 수집 성공 시각

이는 외부 시장 지표가 아니라 아카이브 내부 업데이트 상태다.

#### 주요 업데이트

볼 가치가 높은 카드 5~10개를 노출한다.

- 제목과 요약
- 중요 이유 한 줄
- `주요 변화 / 새 신호 / 후속 업데이트 / 참고` 배지
- 관련 기업·정책·주제
- 출처와 발표일
- 관련 과거 카드 수
- 사용자 해석 수

#### 전체 업데이트

정책·지원 / 기업·투자 / 기술·시장 탭으로 모든 신규 카드를 탐색한다.

### 6.2 카드 상세 `/cards/[id]`

- 제목·요약·중요 이유
- 발표일과 수집일
- 대표 출처와 부속 출처
- 관련 기업·주제
- 과거 관련 카드
- 메모·연결·판단
- 관리자에게 품질 문제 신고

### 6.3 기업·주제 타임라인

- 최근 업데이트
- 전체 카드 시간순 목록
- 연결된 기업·정책·기술
- 사용자 해석

### 6.4 검색

Phase 1 검색 범위:

- 제목·요약 전문 검색
- 기업·기관명 유사 검색
- 정책명과 태그
- 기간·출처·주제 필터

PostgreSQL full-text search와 `pg_trgm`을 사용한다.

### 6.5 해석 작성

필수:

- 근거 카드
- 제목 또는 본문
- 작성자·작성 시점

선택:

- 유형: 메모 / 연결 / 판단
- 확신도: 확신 / 추정 / 질문
- 함의
- 앞으로 관찰할 신호

최대 24시간 비공개 초안을 허용한다. 공유 후 수정 이력을 보존한다.

## 7. 정보가치

### 7.1 목적

정보가치는 사실의 절대 점수가 아니라 **오늘 먼저 볼 순서**를 정하기 위한 설명 가능한 규칙이다.

### 7.2 초기 규칙

```text
소스 등급       1급 +3 / 2급 +2 / 3급 +1
명부 매칭       +4
앵커 일치       +1  (명부 미매칭 시)
동시 발생       +2  (최근 7일 동일 태그 카드 3건 이상)
3환 통과 근거   +1
최신성          경과일에 따른 감쇠
중복 가능성     감점
```

가중치는 설정 테이블에서 관리한다.

### 7.3 설명성과 재현성

평가마다 다음을 저장한다.

- 항목별 점수
- 항목별 한 줄 이유
- 규칙 버전
- 평가 시각
- 관리자 수정 전후
- 최종 배지

가중치를 변경하면 동일 규칙 버전으로 과거 결과를 재현할 수 있고, 새 버전으로 재계산할 수 있어야 한다.

### 7.4 소스 등급

| 등급 | 의미 | 예 |
|---|---|---|
| 1급 | 사실·공시 | 정부 공고·선정 명단·공시 |
| 2급 | 1차 발표·연구 | 논문·특허·기업 발표·연구기관 보고서 |
| 3급 | 보도·해석 | 언론 기사·산업 해설 |

등급은 진실 점수가 아니라 원사실과의 거리다.

## 8. 데이터 파이프라인

### 8.1 흐름

```text
L0 수집
  원문·메타데이터
      ↓
L1 판정
  관련성·중복 후보·범위
      ↓
L2 카드화
  요약·깊이·기업·주제·정보가치
      ↓
L3 노출
  오늘·검색·기업/주제 타임라인
      ↓
L4 선택적 해석
  메모·연결·판단
      ↓
L5 브리핑
  Phase 2
```

### 8.2 수집 멱등성

1단 키:

- 기본: `source_key + external_id`
- 대체: `source_key + sha256(canonical_url)`
- 최후: `source_key + sha256(normalized_title + published_date)`

`source_items`에 unique 제약을 둔다.

### 8.3 의미 중복

- 제목 정규화
- `pg_trgm` 유사도
- 발표일 ±3일
- 주요 기업·기관 일치

높은 확신도만 자동 병합한다. 애매한 후보는 `merge_candidates`에서 관리자가 검토한다. 대표 출처를 정하더라도 다른 출처는 `card_sources`에 보존한다.

### 8.4 부분 실패와 재개

`ingestion_runs`에 다음을 저장한다.

- 소스와 실행 ID
- 시작·종료 시각
- 상태
- 수집·신규·업데이트·중복·실패 수
- 오류 유형과 안전한 오류 메시지
- 마지막 성공 커서 또는 워터마크

한 항목의 실패가 전체 배치를 중단하지 않게 한다. 네트워크·429·5xx는 제한된 지수 백오프로 재시도하고, 파싱·검증 실패는 검토 대상으로 남긴다.

### 8.5 자동 노출

- 신뢰된 구조화 소스 + 높은 관련성: 자동 노출
- 높은 명부 매칭의 전문지 RSS: 자동 노출 가능
- 신규 기업·낮은 관련성·중복 불확실: 관리자 검토
- 3환 정보: 통과 이유 확인 후 노출

기준은 설정으로 관리하고 자동 노출 여부를 실행 이력에 기록한다.

## 9. 기술 구조

### 9.1 스택

| 영역 | 선택 |
|---|---|
| Web/BFF | Next.js App Router + TypeScript |
| Database/Auth | Supabase PostgreSQL + Auth + RLS |
| Ingestion | 별도 Node CLI 워커 |
| UI | Tailwind CSS, 자체 최소 컴포넌트 |
| Validation | Zod |
| Test | Vitest, Testing Library, 로컬 Supabase 통합 테스트, E2E 스모크 |
| Search | PostgreSQL full-text + pg_trgm |
| AI | 공급자 추상화; Phase 1은 요약과 깊이 분류 |
| 배포 | Web과 Worker 분리, DB 하나 |

### 9.2 경계

- Next.js는 사용자용 BFF다.
- Server Component는 DB를 직접 조회한다.
- Server Action은 사용자 변경을 처리한다.
- Route Handler는 인증 콜백·웹훅 등 HTTP 경계에만 사용한다.
- 장시간 수집 작업은 Next.js에서 실행하지 않는다.
- 워커는 일반 Node CLI로 구현해 배포 플랫폼을 교체할 수 있게 한다.
- PostgreSQL을 기준 데이터 저장소로 사용한다.
- 벡터 컬럼은 실제 모델과 평가셋이 결정되는 Phase 2에 추가한다.

### 9.3 저장소

```text
apps/
  web/
  worker/
packages/
  domain/
  database/
  config/
  test-fixtures/
supabase/
  migrations/
  tests/
docs/
```

초기에는 `pnpm workspaces`만 사용한다.

## 10. 보안

- `service_role` 키는 워커 프로세스에만 둔다.
- Next.js는 anon 키와 사용자 세션만 사용한다.
- 관리자 작업은 `security definer` 함수로 노출하되 함수 내부에서 `auth.uid()`와 관리자 역할을 검증한다.
- `security definer` 함수는 고정된 `search_path`와 최소 권한을 사용한다.
- 웹 코드에서 `service_role` 참조를 CI로 차단한다.
- `pending` 사용자는 애플리케이션 데이터에 접근할 수 없다.
- 공개 프로필과 이메일·가입 사유를 분리한다.
- 모든 사용자 입력을 서버에서 다시 검증한다.
- 서비스 키·AI 키·원문·토큰을 로그에 남기지 않는다.
- 카드 병합·관리자 수정·사용자 해석 수정은 감사 이력을 남긴다.

Phase 1의 “공개”는 승인된 내부 사용자 전체를 의미한다. 익명 외부 공개는 포함하지 않는다.

## 12. 수용 기준

| 영역 | 기준 |
|---|---|
| 수집 멱등성 | 같은 수집 작업을 연속 3회 실행해도 원천·카드 행 수가 증가하지 않는다 |
| 중복 병합 | 같은 사건의 복수 출처를 주입하면 카드 1건과 모든 부속 출처가 남는다 |
| 보수적 병합 | 애매한 유사 항목은 자동 병합되지 않고 검토 큐에 남는다 |
| 명부 매칭 | 자동 확정된 카드의 기업명은 표본 100건 모두 원문에 존재한다 |
| 정보가치 | 모든 노출 카드에서 점수 구성·이유·규칙 버전을 조회할 수 있다 |
| 재현성 | 동일 입력과 규칙 버전으로 같은 점수를 재계산한다 |
| 부분 실패 | 한 소스 실패 후 다른 소스가 계속 처리되고 실패 이유가 관리자 화면에 보인다 |
| 재개 | 실패 후 마지막 성공 커서부터 누락 구간만 처리한다 |
| RLS | `pending` 토큰으로 주요 테이블을 조회하면 0행이다 |
| 서비스 키 격리 | Web 소스·서버 번들에 `service_role` 참조가 없다 |
| 오늘 화면 | 사용자가 5분 안에 오늘의 주요 변화 3건을 설명할 수 있다 |
| 카드 품질 | 사용자 표본 평가에서 주요 카드의 70% 이상이 볼 가치가 있다 |

## 13. 성공 지표

### 13.1 북극성 지표

> **주간 유효 정보 소비 사용자 수**

해당 주에 다음 중 하나를 수행한 고유 사용자:

- 오늘의 주요 업데이트 3건 이상 열람
- 기업·주제 타임라인 탐색
- 검색으로 과거 카드 열람
- 메모·연결·판단 작성

### 13.2 Phase 1 목표

| 지표 | 목표 |
|---|---|
| 주간 활성 사용자 | 5명 이상 |
| 활성 사용자의 주 3일 이상 방문율 | 50% 이상 |
| 주요 업데이트 클릭률 | 40% 이상 |
| 카드 품질 만족도 | 70% 이상 |
| 과거 정보 탐색이 포함된 세션 | 30% 이상 |
| 카드→해석 전환율 | 5% 이상, 보조 지표 |

해석 생성률은 장기 차별성 지표지만 Phase 1의 존속 조건은 아니다.

## 16. ChatGPT/Codex와 Claude 역할 분담

역할과 아티팩트 소유권을 함께 사용한다.

| 아티팩트·업무 | 주 책임 | 다른 쪽 |
|---|---|---|
| PRD와 제품 결정 | 사용자 + Claude 초안 | Codex가 구현 영향·이견 제안 |
| ADR·불변조건·수용 기준 | Claude 초안 | Codex가 실행 가능성 검토 |
| 마이그레이션·RLS 파일 | Codex 구현 | Claude가 스키마·보안 리뷰 |
| 애플리케이션·워커 코드 | Codex | Claude가 diff 리뷰 |
| 테스트 코드와 실행 | Codex | Claude가 누락 시나리오 제안 |
| 최종 제품 선택 | 사용자 | 두 모델이 대안과 근거 제공 |

### 16.1 중단이 필요한 결정

Codex는 다음 변경이 필요하면 구현을 멈추고 사용자 결정 또는 ADR 개정을 요청한다.

- 제품 범위
- 스키마의 핵심 관계와 불변조건
- 인증·권한·외부 공개
- 유료 외부 서비스나 비용 상한
- 데이터 삭제·원문 저장 정책

### 16.2 Codex가 자율 결정할 수 있는 것

- 되돌리기 쉬운 내부 구현
- 컴포넌트·함수 분리
- 테스트 보조 구조
- 코드 스타일과 이름
- 이미 승인된 수용 기준을 충족하기 위한 버그 수정

중요한 내부 결정은 `docs/decisions/`에 짧게 기록한다.

### 16.3 작업 절차

1. Claude 또는 사용자가 수직 절편의 결정·불변조건·수용 기준을 확정한다.
2. Codex가 작은 수직 절편을 구현하고 테스트한다.
3. Codex가 `HANDOFF.md`에 변경·테스트·남은 위험을 기록한다.
4. Claude가 P0/P1/P2와 수용 기준 중심으로 리뷰한다.
5. Codex가 수용·보류·반박과 이유를 결정 기록에 남긴다.
6. 수정과 검증 후 다음 절편으로 이동한다.
